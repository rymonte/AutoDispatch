# Hoppie integration: static discovery

**Status:** research, design and bounded user-performed live check, 17 November 2026; not implementation approval. Issue [#18](https://github.com/rymonte/AutoDispatch/issues/18) covers M09, D03, AC07, DEC-038, DEC-039, DEC-055 and open PRE-06; DEC-057 and DEC-059 also govern recovery and uncertain outcomes. Scope is outbound preliminary dispatch only. The PRD remains authoritative.

## Evidence

- **Official documented capability, high confidence in the documentation, not live enforcement:** [Hoppie API](https://www.hoppie.nl/acars/system/tech.html), reviewed 17 November 2026, describes store-and-forward, a recipient polling the queue, TELEX, GET/POST fields `logon`, `from`, `to`, `type`, `packet`, and a 15-second connection timeout. It documents a 100-second callsign lock per logon code and network, renewed by qualifying connections; a competing code receives `callsign already in use`. It does not establish cockpit display or sender-format limits. Server storage can be less than 24 hours.
- **Third-party source inspection, medium confidence about the inspected code only:** [ACARS Link protocol](https://github.com/availoff/acars-link/blob/25c7d568e850be5ae456ccb873ca80362e139182/packages/transport/src/hoppie/protocol.ts) and [transport](https://github.com/availoff/acars-link/blob/25c7d568e850be5ae456ccb873ca80362e139182/packages/transport/src/hoppie/transport.ts), commit `25c7d568e850be5ae456ccb873ca80362e139182`, reviewed 17 November 2026. It sends form-encoded POST over HTTPS, parses `ok` and `error` bodies, uses a 15-second timeout and delays callsign conflicts 110 seconds. Its 2–16 uppercase alphanumeric callsign rule is explicitly a client assumption, not a verified Hoppie limit. The user subsequently reported a successful HTTPS/POST test as described below. Its broad retry of timeouts and other request failures is incompatible with M09. Its proprietary code is a behavioural reference only; do not copy it.
- **Unofficial documentation, corroboration only:** [connection notes](https://github.com/devHazz/hoppie-acars-docs/blob/5563f66ed1b553ad6188f580c60d8dae8945c9b7/System/Connection.md), commit `5563f66ed1b553ad6188f580c60d8dae8945c9b7`, reviewed 17 November 2026, describe the same fields and polling model. They do not validate AutoDispatch or aircraft compatibility.

The issue comment identifies ACARS Link; no Smart ACARS repository was identified in that comment. No source inspection here proves either application's claimed real-world operation or establishes AutoDispatch compatibility.

## Proposed approach

Generate and persist the local message first, independently of configuration or network success. Freeze its body, the current inbound callsign as recipient and preferred `AD` plus that callsign as sender; identify the next leg in the body. No first-leg preliminary message is generated. Preserve the message and frozen identities through leg activation and recovery as required by M09 and DEC-057. Unsupported sender values must be reported, never silently truncated or replaced.

The backend integration in the utility process would submit a compact plain-text TELEX using the user's credential; the pure domain owns message and outcome policy through a port. Main handles safeStorage operations, and React displays snapshots and sends commands, consistent with [boundaries](boundaries.md). Use an HTTPS form POST with all fields in the body as a candidate, supported by the one user-reported test; never log the credential, request body or credential-bearing URL. Avoid gratuitous polling: the aircraft's independently configured client retrieves the message. A single ping may test connectivity but does not prove sending or receipt.

Treat a recognized positive server response as **accepted**, not delivered or read. Treat an explicit documented conflict as **rejected conflict**; other understood rejections as **rejected**, with no automatic retry unless a safe policy is established. A timeout, interrupted request, malformed or unrecognized response, HTTP failure of uncertain provenance, or crash after dispatch and before durable outcome is **unknown**, not rejection. Only a demonstrably pre-submission failure is safely retryable as such; do not infer that from a generic network error. Never automatically resend accepted or unknown submissions, including on restart. Local read state is independent of cockpit state.

### Retry direction — 17 November 2026

The user specifies up to three retries after the initial attempt, starting at 30 seconds with backoff; an explicit callsign conflict instead waits 100 seconds between attempts. Apply the same overall retry limit to the message. The backoff multiplier and any cap remain unspecified; a 30/60/120-second sequence is a proposal, not an agreed parameter. Retry only a confirmed rejection eligible for retry or a demonstrably pre-submission failure; a timeout or lost response is uncertain and must not be resent automatically. The 100-second lock is renewable, so waiting 100 seconds after rejection does not guarantee release. Preserve the original sender, recipient and content, and stop on acceptance or exhaustion.

Proposed restart and expiry design, still open: persist attempt count, deadline and frozen payload before scheduling; resume only a durable known-safe wait while the message remains valid. An in-flight or uncertain attempt becomes unknown on restart. Cancel pending retries on rotation replacement/clear, message invalidation or expiry; do not cancel merely because the next leg activated. An absolute expiry must be agreed. Exhaustion leaves the local log and rotation usable. Use a wall-clock deadline for network scheduling, not simulator time; handle clock changes conservatively. No conflict or retry has been live-tested.

## Remaining validation

The user considers issue #18 complete as a discovery and design investigation based on the request research and cockpit check. Its original full validation criteria are not all met; closing the issue does not close PRE-06 or imply those checks passed. Carry the remaining design and verification work under PRE-06 and implementation tracking.

PRE-06 stays open. Establish authoritative sender length and character constraints and verify `AD<inbound callsign>` without truncation, including representative boundary values and display in a named aircraft/client version. Confirm conflict response syntax and distinguish a genuine conflict rejection from malformed, intermediary and lost responses; the reviewed source parser is not authoritative. The single HTTPS POST check does not establish general compatibility or response semantics. Same-callsign collisions remain possible even with a distinctive prefix; same-code sharing does not guarantee deterministic recipient behaviour.

A separately authorised controlled check should name the aircraft, version, account/network and test window; the user configures the aircraft client and matching inbound callsign. Record sanitised sender, recipient, request outcome and timestamps, then separately observe cockpit receipt and display. Include a controlled conflict using distinct codes only if specifically authorised; do not expose credentials or unrelated network traffic. Record failures, ambiguity, limitations and aircraft coverage. Acceptance alone cannot establish receipt, and a negative result does not close the gate. No live network or simulator operation is authorised by this document.
