# Navigraph and SimBrief: integration discovery

**Reviewed:** 18 November 2026. **Status:** public documentation/forum research and unauthenticated catalogue retrieval; no authenticated generation, SDK execution or application compatibility test. Supports [PRD](../../prd.md) D01, M02/M06/M08/M09, questions 1–4/8/15/21/22 and PRE-01/PRE-02; tracked by issues [#13](https://github.com/rymonte/AutoDispatch/issues/13) and [#14](https://github.com/rymonte/AutoDispatch/issues/14). No baseline gate is closed by this research.

## What the V2 forum evidence establishes

Two public threads discuss credentials and privately supplied documentation:

- [9 July 2026: missing endpoint documentation](https://forum.navigraph.com/t/api-v2-jwt-no-endpoint-documentation/23817): a developer reports credentials with `openid`, `simbrief`, `ofp` and `offline_access`; a staff response says further instructions were emailed, and the developer confirms receipt.
- [24 August 2026: missing V2 attachment](https://forum.navigraph.com/t/simbrief-api-v2-endpoint-documentation-never-arrived-ticket-37604/24168): a developer reports those scopes and a working device flow but missing endpoint documentation; staff offer a private reply.

**Evidence classification:** developer-reported scopes/working authentication, accompanied by public staff follow-up. This supports the existence of a V2 credential/documentation path. It does not expose its endpoint contract, establish what the reported scopes permit, or grant AutoDispatch access. The August question concerns OFP retrieval; it is not a demonstration of unattended generation.

The [March 2024 blind-generation discussion](https://forum.navigraph.com/t/simbrief-api-blind-generation/15203) records staff saying the then-current API required its popup and that a future version would use newer methods. Treat that as historical V1 evidence, not a finding that V2 generation is unavailable today. No public source inspected in this pass establishes the required unattended-generation or preview contract. Private documentation may answer it.

M08 returned-value validation remains required.                                                         |
| Planning inputs and units        | The [public guide](https://developers.navigraph.com/docs/simbrief/using-the-api) documents departure time, taxi-in/out, runway, fuel and aircraft-limit inputs. Its `acdata` weight convention differs from display units: generally thousands of pounds, with passenger weight in pounds. The [forum reference](https://forum.navigraph.com/t/the-simbrief-api/5298) also documents baggage weight in pounds. | Map each supported request/response field independently; do not apply the OFP's KG/LBS display preference to every input. V2 field names, fuel semantics and scheduled/filed event meanings still need representative responses. |
| Optional saved-airframe ID       | The [API reference](https://forum.navigraph.com/t/the-simbrief-api/5298) documents supplying an Internal ID instead of aircraft type; subsequent profile changes affect generation and deletion can invalidate it.                                                                                                                                                                                             | This is not enumeration of a user's saved airframes. Confirm how the approved generation API accepts the identifier.                                                                                                             |

**Static-ID regression evidence:** [staff identified a reset bug in July 2023 and reported its fix in August](https://forum.navigraph.com/t/static-id-getting-cleared/12710) when website regeneration selected new runways/alternates. That thread's version 2.15.0 is a SimBrief application release, not proof of generation API V2. Retain a validation case covering refreshed weather/runway inputs and plan association. The same thread treats callbacks as a suggestion, not a supported webhook contract.

**Assumption A-SB-01:** the product owner expects the newer API to preserve `static_id` or equivalent correlation. Record this as plausible continuity, not a verified capability. Confirm both the field and repeated-submission semantics; a stable identifier alone cannot establish exactly-once processing.

The [aircraft-data support discussion](https://forum.navigraph.com/t/acdata-through-api/10545) further confirms the thousands-of-pounds convention and the need to encode structured inputs correctly. It is supporting evidence for field-level validation, not permission to reproduce the legacy HTML/PHP implementation in the desktop app.

## Catalogue versus personal saved airframes

The [official catalogue announcement](https://forum.navigraph.com/t/getting-currently-supported-aircraft-layout-options/5296) and [November 2024 staff reply](https://forum.navigraph.com/t/supported-aircraft-airframe-profiles/17675) document public aircraft/layout and detailed airframe lists.

Read-only checks on 18 November 2026 returned HTTP 200 and parseable JSON from:

- [Aircraft/layout catalogue](https://www.simbrief.com/api/inputs.list.json): top-level `aircraft`, `layouts`, `last_updated`, `process_time`.
- [Detailed airframe catalogue](https://www.simbrief.com/api/inputs.airframes.json): entries grouped by aircraft type codes.

These establish endpoint availability at the observation time, not complete schema stability or generation compatibility. No personal account data or OFP was requested. Catalogue/manual setup remains the accepted MVP fallback; this is not a reason to require users to import IDs in bulk.

Personal listing remains unconfirmed. The [2022 staff answer](https://forum.navigraph.com/t/retrieving-a-users-fleet-through-api/10221) says it was not public then; the [August 2026 personal-airframe request](https://forum.navigraph.com/t/pull-saved-airframes-data-via-api/24032) still has no visible answer in this review. Neither establishes its availability for approved V2 clients today.

## Focused questions remaining for Navigraph

1. Which approved client setup, scopes and SDK/authentication flow permit unattended generation directly from this desktop application? Request the current V2 specification as a link if attachments are unreliable.
2. Can a calculation return fuel/time estimates without saving an OFP or changing the user's latest plan? Otherwise, can the same saved flight be edited/regenerated with refreshed planning inputs?
3. Does V2 retain `static_id`, or what replaces it? What happens when two requests reuse it, including after timeout? Distinguish correlation, replacement and idempotency explicitly.
4. What are the job/status/result, timeout, cancellation and rate-limit contracts? Validate the accepted DEC-059 initial-plus-three retry policy against provider limits; this policy accepts possible remote duplicates on uncertain failures and must not be silently reverted.
5. How are `maxpax`, explicit passenger count, airframe overrides, fuel/alternate fields and input/output units interpreted? Obtain representative responses for PRE-02.
6. Is personal saved-airframe enumeration available, and with which scopes/schema? Keep the documented public catalogue and optional-ID fallback independent of that answer.

PRE-01 and PRE-02 remain open. Public authentication, legacy input/correlation and catalogue facts narrow the investigation; they do not establish unattended generation, preview support or AutoDispatch approval. Hoppie's separate conservative unknown-outcome policy is unchanged.
